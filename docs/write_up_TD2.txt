==================================================
PARTIE 0 - LE MODELE DE RESSOURCES (questions)
==================================================

1. Projet / région / zone :
   - projet = frontière administrative (ressources, droits, quotas, APIs, facturation)
   - région = zone géographique (ex : europe-west9 = Paris)
   - zone = un datacenter dans une région (europe-west9-a, -b, -c)

2. Une VM est une ressource ZONALE (elle vit dans une seule zone).
   Vu dans les URLs : machineType -> /zones/..., subnetwork -> /regions/..., network -> /global/...
   Donc : réseau global -> sous-réseau régional -> VM et disque zonaux.

3. Type de machine = le matériel (vCPU + RAM). Image = le système d'exploitation.

4. Image = le modèle. Disque de démarrage = la copie persistante créée à partir de l'image,
   qui contient l'OS + mes fichiers.

5. Un type peut être dans le catalogue d'une zone mais sans serveur physique libre au moment
   de la demande. Vécu : e2-standard-2 listée dans europe-west9-a mais création refusée
   (ZONE_RESOURCE_POOL_EXHAUSTED). Le cloud a des serveurs réels en nombre limité.

PARTIE 3 - TYPES DE MACHINES

gcloud compute machine-types list --filter="zone:($ZONE) AND name~'^e2-'"
   ATTENTION : apostrophes droites ' et pas celles du PDF ’

Lire un nom : e2 - standard - 2  =  série - profil - nombre de vCPU
   e2 / n2 / n2d / n4 / t2d   -> usage général (e2 = la moins chère)
   c3 / c4 / c4d              -> optimisées calcul
   m3                         -> optimisées mémoire (jusqu'à 3904 Go !)
   highcpu  = 1 Go par vCPU   (e2-highcpu-2 : 2 vCPU, 2 Go)
   standard = 4 Go par vCPU   (e2-standard-2 : 2 vCPU, 8 Go)
   highmem  = 8 Go par vCPU   (e2-highmem-2 : 2 vCPU, 16 Go)
   -lssd    = avec Local SSD
   e2-micro / small / medium = coeur PARTAGE (perfs irrégulières, mauvais pour benchmark)

export MACHINE_TYPE="e2-standard-2"
gcloud compute machine-types describe "$MACHINE_TYPE" --zone="$ZONE"

   guestCpus: 2

   isSharedCpu: false     (vCPU réservés)
   architecture : pas affichée (vérifiée plus tard avec lscpu : x86_64)
   zone: europe-west9-a
   (creationTimestamp 1969 = le "zéro" des horloges, pas une vraie date)

Questions :
1. 2 vCPU, 8 Go de RAM.
2. Un vCPU = en général un thread matériel (hyperthread) d'un processeur physique.
   Vérifié : 2 vCPU = 1 seul coeur physique avec 2 threads.
3. Même nombre de vCPU mais processeurs différents (génération, fréquence, cache, Intel/AMD).

--------------
CORRECTION DU SCRIPT benchmark.sh
--------------

2 problèmes dans le script du TD1 :
1. le CSV de sortie était écrit en dur (data/benchmark_local.csv)
   -> sur la VM, les mesures cloud se seraient mélangées aux mesures locales
2. runtime_s était le "Elapsed" de GNU time au format 0:00.06
   -> pas un nombre, et précision au centième seulement
   -> alors que le programme donne runtime_s précis dans son JSON, mais on l'envoyait dans /dev/null

Modifications (faites sur la VM avec nano puis sed) :

a) nouvelle ligne après REPETITIONS=$3 :
   FICHIER=${4:-data/benchmark_local.csv}
   ${4:-x} = 4e argument, ou x par défaut s'il n'y en a pas

b) remplacer le chemin en dur par $FICHIER partout sauf sur la ligne FICHIER= :
   sed -i '/^FICHIER=/!s#data/benchmark_local\.csv#$FICHIER#g' scripts/benchmark.sh
   sed -i = modifie le fichier sur place
   /^FICHIER=/! = sur les lignes qui ne commencent PAS par FICHIER=
   s#ancien#nouveau#g = remplacer (# comme séparateur car le chemin contient des /)

c) garder la sortie JSON au lieu de la jeter :
   sed -i 's#> /dev/null#> sortie_temp.txt#' scripts/benchmark.sh
   >  = sortie normale (le JSON)       2> = sortie d'erreur (le rapport de GNU time)

d) lire runtime_s dans le JSON (ligne 49) + mettre à jour le commentaire (ligne 48) :
   sed -i '49c\    TEMPS=$(grep -o "runtime_s[^,}]*" sortie_temp.txt | cut -d: -f2)' scripts/benchmark.sh
   grep -o = ne garde que le morceau trouvé -> runtime_s":0.096345277
   cut -d: -f2 = coupe au ":" et garde le 2e morceau -> 0.096345277

e) supprimer aussi le nouveau fichier temporaire :
   sed -i 's#rm resultat_temp.txt#rm resultat_temp.txt sortie_temp.txt#' scripts/benchmark.sh

Vérifs : grep -n 'FICHIER' scripts/benchmark.sh / sed -n '48,50p' scripts/benchmark.sh

Test : bash scripts/benchmark.sh cpu_task 200000 2 data/test.csv
   -> runtime_s = 0.041332393 (vrai nombre) ; puis rm data/test.csv

   -> {"task":"cpu_task","size":200000,"runtime_s":0.042304536,"primes_found":17984}

--command = se connecte, exécute, affiche, se déconnecte. && = "puis, si ça a marché".
Base de l'automatisation : piloter des VMs depuis un script sur mon PC.

PIEGE découvert plus tard : avec --command, `go` = /usr/bin/go = 1.22.2 !
Le ~/.bashrc d'Ubuntu s'arrête au début si la session n'est pas interactive,
donc notre ligne export PATH (ajoutée à la fin) n'est jamais lue.
Pas d'impact sur les mesures (binaires compilés en session interactive avec 1.26.0),
mais pour automatiser une compilation à distance : utiliser /usr/local/go/bin/go en entier.

==================================================
QUESTIONS D'ANALYSE
==================================================

1. La VM est-elle plus rapide pour tous les workloads ?
   Non, pour aucun. Mais l'écart dépend du workload : x4-5 en calcul pur, x1,4 en matrices,
   ~x1 en mémoire.

2. Pourquoi "cloud" n'est pas une spécification de perf ?
   "Une VM cloud" peut être n'importe quel processeur. Ici un Broadwell de 2016 ; une
   c4-standard-2 aurait un CPU récent. Même deux e2-standard-2 peuvent tomber sur des
   CPU différents. Il faut dire QUELLE machine.

3. La mémoire est-elle la même en local et dans le cloud ?
   Oui, quasi identique : elle dépend du programme et de la version de Go, pas de la machine.

4. Les temps répétés sont-ils identiques sur la VM ?
   Non. Calcul très stable (<2 % pour cpu_task, plus stable que mon laptop : 20 % en local
   sur cpu_task 500000). Mais memory_task a des pics (0.81 s vs 0.39 s), et le 1er essai
   est souvent plus lent.

5. Quelles caractéristiques noter pour être reproductible ?
   Type de machine, zone, modèle exact du CPU (lscpu), coeurs/threads, RAM, image exacte
   de l'OS, version de Go, méthode de mesure (runtime_s interne), nombre de répétitions,
   tailles utilisées.
